1. Problem Statement and Motivation

A typical neighbourhood gym runs on a register book, a spreadsheet of members and a WhatsApp group. That works for fifty people but breaks as the gym grows: memberships expire without anyone noticing, popular classes are overbooked while others stay empty, two trainers get booked into the same room, payments are hard to reconcile, and nobody can say which members are about to stop coming.

IronPulse is a web-based gym management system that replaces this with one source of truth. It covers the whole member life-cycle — registration, buying and renewing plans, freezing them, checking in at the front desk, booking group classes with an automatic waitlist, requesting personal training, following workout plans and logging workouts — and gives the owner live business reports.

The problem is a good fit for a polyglot database design. Money, capacity and time slots need strict consistency (ACID transactions, constraints, triggers), which is why they live in MySQL. Workout plans, workout logs and body measurements are deeply nested, change shape often and are mostly read as whole documents, which is why they live in MongoDB. The project is therefore not a CRUD form over one table: the business rules are enforced inside the databases themselves.

2. Objectives

  1. Design a normalised relational schema (ER model → relations) for members, plans, memberships, payments, classes, bookings, personal training and attendance, with every rule that can be expressed declaratively written as a key, foreign key or CHECK constraint.
  2. Enforce the remaining business rules in the database with triggers, stored procedures and functions, so the data stays correct even if the application has a bug.
  3. Use transactions and row locks for operations that touch several rows (buying a plan, booking the last seat, promoting from the waitlist, completing a paid PT session).
  4. Model training data as MongoDB documents with schema validation, and compute progress statistics with aggregation pipelines.
  5. Build a Next.js web interface with three roles (admin, trainer, member), forms, tables, search, filters and dashboards, connected through a server-side data-access layer.
  6. Apply security basics: hashed passwords, signed session cookies, role checks on every page and action, credentials only in environment variables, and a least-privilege database account for the app.
  7. Prove correctness with an automated test suite that runs against the real databases.

Non-functional

  • Integrity: invalid data is refused by the database (constraints, triggers, validators), not only by the forms.
  • Concurrency: two people booking the last seat or buying overlapping plans at the same moment cannot both succeed (row locks).
  • Security: bcrypt password hashes, httpOnly signed JWT cookie, prepared statements, no credentials in code, app account without DDL rights.
  • Auditability: every change to memberships, payments and PT sessions is written to audit_log by triggers.
  • Maintainability: plain JavaScript and raw SQL (no ORM) so every query can be explained; one script rebuilds both databases.

5. System Architecture

IronPulse is a three-tier web application.

  • Presentation: pages are React Server Components rendered on the server, so the browser receives ready HTML (tables, forms, SVG charts). Forms submit to Server Actions; a few small client components only keep form state and show messages.
  • Application / API layer: the Next.js 16 server. src/proxy.js checks the session cookie before any protected page; every page and action then calls requireRole() from src/lib/auth.js, which verifies the JWT and re-reads the user from MySQL. src/lib/db.js wraps a mysql2 connection pool (prepared statements, callProcedure() for stored procedures, transaction() for multi-statement work) and src/lib/mongo.js holds one shared MongoDB client.
  • Data: MySQL 8 (gym_db) and MongoDB 8 (gym_mongo). The app connects to MySQL as gym_app, which may only SELECT, INSERT, UPDATE, DELETE and EXECUTE. Tables, triggers, routines and events are created once by npm run db:setup using the MySQL root account.

All connection settings and the session secret come from .env.local, which is not in Git (.env.example lists the names).

6. Database Design

6.1 ER diagram

Notation: rectangles are entity types, diamonds relationship types, ovals attributes (key attributes underlined, derived attributes dashed). A double line means total participation (min ≥ 1); each line carries the (min,max) pair of the entity it touches.

  • Specialisation: USER is specialised (disjoint, partial) into MEMBER and TRAINER. Admins are users that belong to neither subclass.
  • Weak entity: ATTENDANCE (a visit) has no identity of its own; it is identified by its owner MEMBER through the identifying relationship CHECKS_IN and the partial key Check_in.
  • M:N relationship with attributes: BOOKS between MEMBER and CLASS_SESSION carries Status and Booked_at (Booked_at decides the waitlist order).
  • Composite attribute: Emergency_contact(Name, Phone). Derived: Age, Days_left, Seats_left, Duration — computed in views, never stored.
  • Roles: a PAYMENT is made by a member (Payer) and may be recorded by a staff user (Recorder); a PAYMENT pays for exactly one MEMBERSHIP or one PT_SESSION.
  • AUDIT_LOG stands alone: it is written only by triggers and refers to rows by table name and id.

6.3 Relational schema

6.4 Normalisation

All tables are in third normal form: every non-key column depends on the whole key and only on the key. Repeating or multi-valued data was split out (a member's memberships, a class's bookings, a member's visits), and descriptive data is stored once (plan details in membership_plans, room capacity in rooms, trainer rates in trainers). Values that could be derived are not stored; they are computed by views.

Three columns look redundant but are deliberate:

  • pt_sessions.price and class_sessions.capacity are snapshots: a trainer's rate or a room may change later, but a past session must keep the price and capacity it had.
  • payments.member_id records the payer directly, so payment history needs no join through two optional foreign keys.
  • members.member_code is the code printed on the card. It is derived from user_id once, at registration, and its format is guarded by a CHECK constraint.

6.5 MongoDB document model

Embedding was chosen where data is always read together (a plan's days and exercises; a log's sets). References are used across databases: memberId, trainerId and userId hold MySQL primary keys, and the app checks them in MySQL before writing to MongoDB. Inside MongoDB, logs point to plans and exercises by ObjectId.

6.6 Database choice and justification

DataWhereWhy
Users, members, trainers, plans, memberships, paymentsMySQLMoney and entitlements must be exact. Foreign keys, CHECK constraints and ACID transactions guarantee, for example, that a refund and its membership cancellation happen together.
Classes, bookings, PT sessions, attendanceMySQLCapacity and time-slot rules need row locks and triggers (no double-booking, waitlist order, clash detection), and reports need JOINs, GROUP BY and window functions.
Workout plans and logsMongoDBNaturally nested (plan → days → exercises; log → exercises → sets) with a variable shape (weights, timed holds, cardio). One document read replaces 4–5 joins, and the aggregation pipeline computes progress.
Body measurementsMongoDB time-seriesAppend-only measurements over time; the time-series collection stores and groups them efficiently.
NotificationsMongoDBShort-lived inbox items with free-form metadata; a TTL index deletes them after 60 days.
Exercise libraryMongoDBArrays of muscles, equipment, tags and instructions; a weighted text index gives ranked search.

Q10. Stored procedure sp_book_class (transaction + row lock)

Shows: START TRANSACTION / COMMIT, SELECT … FOR UPDATE row lock so two members cannot take the last seat at the same time, business rules raised with SIGNAL SQLSTATE '45000', EXIT HANDLER that rolls back, OUT parameters. Called from the member Classes page with CALL sp_book_class(?, ?, @id, @status).

CREATE PROCEDURE sp_book_class(IN p_member_id INT UNSIGNED, IN p_class_session_id INT UNSIGNED,
                               OUT o_booking_id INT UNSIGNED, OUT o_status VARCHAR(12))
BEGIN
    DECLARE v_capacity SMALLINT UNSIGNED;
    DECLARE v_starts DATETIME;
    DECLARE v_session_status VARCHAR(12);
    DECLARE v_taken INT;
    DECLARE v_weekly_limit TINYINT UNSIGNED;
    DECLARE v_membership_id INT UNSIGNED;
    DECLARE v_existing_id INT UNSIGNED DEFAULT NULL;
    DECLARE v_existing_status VARCHAR(12) DEFAULT NULL;
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        RESIGNAL;
    END;

    START TRANSACTION;
        SELECT capacity, starts_at, status INTO v_capacity, v_starts, v_session_status
        FROM class_sessions WHERE class_session_id = p_class_session_id
        FOR UPDATE;

        IF v_starts IS NULL THEN
            SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Class not found';
        END IF;
        IF v_session_status <> 'scheduled' OR v_starts <= NOW() THEN
            SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'This class is no longer open for booking';
        END IF;

        SET v_membership_id = fn_active_membership_id(p_member_id, DATE(v_starts));
        IF v_membership_id IS NULL THEN
            SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'You need an active membership on the day of this class';
        END IF;

        SELECT p.classes_per_week INTO v_weekly_limit
        FROM memberships ms JOIN membership_plans p ON p.plan_id = ms.plan_id
        WHERE ms.membership_id = v_membership_id;
        IF v_weekly_limit IS NOT NULL
           AND fn_classes_booked_in_week(p_member_id, DATE(v_starts)) >= v_weekly_limit THEN
            SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Weekly class limit of your plan reached';
        END IF;

        SELECT booking_id, status INTO v_existing_id, v_existing_status
        FROM class_bookings
        WHERE class_session_id = p_class_session_id AND member_id = p_member_id;
        IF v_existing_status IN ('booked','waitlisted') THEN
            SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'You have already booked this class';
        END IF;

        SELECT COUNT(*) INTO v_taken
        FROM class_bookings
        WHERE class_session_id = p_class_session_id AND status = 'booked';

        SET o_status = IF(v_taken < v_capacity, 'booked', 'waitlisted');

        IF v_existing_id IS NOT NULL THEN
            -- re-booking after an earlier cancellation: goes to the back of the queue
            UPDATE class_bookings SET status = o_status, booked_at = CURRENT_TIMESTAMP(3)
            WHERE booking_id = v_existing_id;
            SET o_booking_id = v_existing_id;
        ELSE
            INSERT INTO class_bookings (class_session_id, member_id, status)
            VALUES (p_class_session_id, p_member_id, o_status);
            SET o_booking_id = LAST_INSERT_ID();
        END IF;
    COMMIT;
END$$

Q11. Trigger trg_attendance_bi (validation in the database)

Shows: BEFORE INSERT trigger that refuses a check-in when the membership is frozen, missing/expired, or the member is already inside — even if a bug in the app tried to insert the row.

CREATE TRIGGER trg_attendance_bi BEFORE INSERT ON attendance FOR EACH ROW
BEGIN
    IF EXISTS (SELECT 1 FROM memberships
               WHERE member_id = NEW.member_id AND status = 'frozen'
                 AND DATE(NEW.check_in) BETWEEN start_date AND end_date) THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Membership is frozen. Unfreeze it to check in';
    END IF;

    IF NOT EXISTS (SELECT 1 FROM memberships
                   WHERE member_id = NEW.member_id
                     AND status IN ('active','expired')
                     AND DATE(NEW.check_in) BETWEEN start_date AND end_date) THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Member has no active membership for today';
    END IF;

    IF EXISTS (SELECT 1 FROM attendance
               WHERE member_id = NEW.member_id AND check_out IS NULL) THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Member is already checked in';
    END IF;
END$$

Q13. Scheduled event ev_class_housekeeping

Shows: MySQL Event Scheduler running a procedure every 15 minutes: finished classes → completed, unattended bookings → no_show, forgotten check-outs closed after 4 h, stale PT requests cancelled.

CREATE PROCEDURE sp_close_finished_classes()
BEGIN
    UPDATE class_bookings cb
    JOIN class_sessions cs ON cs.class_session_id = cb.class_session_id
    SET cb.status = CASE cb.status WHEN 'booked' THEN 'no_show' ELSE 'cancelled' END
    WHERE cs.status = 'scheduled' AND cs.ends_at < NOW()
      AND cb.status IN ('booked','waitlisted');

    UPDATE class_sessions SET status = 'completed'
    WHERE status = 'scheduled' AND ends_at < NOW();

    UPDATE attendance SET check_out = check_in + INTERVAL 4 HOUR
    WHERE check_out IS NULL AND check_in < NOW() - INTERVAL 4 HOUR;

    UPDATE pt_sessions SET status = 'cancelled'
    WHERE status = 'requested' AND starts_at < NOW();
END$$

CREATE EVENT ev_class_housekeeping
    ON SCHEDULE EVERY 15 MINUTE
    DO CALL sp_close_finished_classes();

13. Conclusion and Future Enhancements

IronPulse meets the project brief with a MySQL + MongoDB design in which each database stores the data it suits best. The relational side keeps money, capacity and schedules consistent through 22 CHECK constraints, 18 triggers, 13 stored procedures and transactional row locks; the document side stores nested training data with schema validation and computes progress with aggregation pipelines. The Next.js interface gives three roles their own workflows, and every rule shown in the interface is enforced again in the database. The automated suite (55 of 55 cases passed) and the manual browser tests show that invalid operations are refused with clear messages and valid ones update every related row together.

What we learned: moving rules into the database (triggers and procedures instead of only form checks) made the app code smaller and removed a whole class of bugs; and picking the database by the shape of the data made both sides simpler than forcing everything into one model.

Future enhancements

  • Semantic search: store exercise and trainer-bio embeddings (e.g. in MongoDB Atlas Vector Search or pgvector) so "something for my knees" finds low-impact exercises without matching words.
  • Online payments through a payment gateway with webhooks, replacing the simulated member self-purchase.
  • E-mail / SMS reminders for renewals and classes, and password reset by e-mail.
  • QR-code check-in at the door and a mobile app.
  • Multi-branch support (a branches table, branch-scoped admins and reports).
  • More flexible trainer plan builder (more than 3 days, custom sets and reps per member).

Appendix: How to Run

  1. Install Node.js 20.11+, MySQL 8 and MongoDB 8; clone https://github.com/SUKRUTH-ES/ironpulse-gym-management.
  2. npm install
  3. Copy .env.example to .env.local and fill in the MySQL root password (used only by the setup script), a random MYSQL_PASSWORD for the app account and a random SESSION_SECRET.
  4. npm run db:setup — builds both databases and loads demo data (drops existing data).
  5. npm run dev and open http://localhost:3000. Demo logins are listed in the README.

Documentation tools (in docs/tools/): node docs/tools/dump-schema.mjs, python docs/tools/make_schema.py, python docs/tools/make_dictionary.py, node docs/tools/run-queries.mjs, node docs/tools/screenshots.mjs, node docs/tools/run-tests.mjs + python docs/tools/make_testdoc.py, then python docs/tools/build_report.py (course report) and python docs/tools/build_full_report.py (this document).
